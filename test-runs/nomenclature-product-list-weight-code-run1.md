## Контекст

Ранее в этой же сессии весь список товаров модели «iPhone 13» (~40 строк) пострадал от параллельного действия QA Lead (вес 350g → 3.33g на всех строках) — инцидент не связан с этим прогоном, восстановлен и подтверждён до начала валидационного тестирования (см. переписку с QA Lead). Перед началом этого прогона весь список подтверждён в состоянии 350g.

## Механизм редактирования (подтверждено эмпирически)

- Вес и код редактируются как инлайн в самой таблице списка (клик по ячейке → текстовое поле), так и через модальное окно «Edit product» (идентичные поля). Сохранение инлайн — по Enter; Escape отменяет несохранённое изменение без запроса подтверждения.
- Полный цикл редактирования имеет заметную серверную задержку (до 2–3 сек) между нажатием Enter и обновлением значения в DOM — при проверке результата нужно выдерживать паузу перед скриншотом/чтением DOM, иначе создаётся ложное впечатление, что изменение не сохранилось.

## Ошибка методологии (зафиксировано для будущих прогонов)

При первой попытке теста NOM-F-C01 использовался `Ctrl+A` для выделения текста перед вводом — в этом конкретном инпуте `Ctrl+A` не выделил текст, из-за чего новый текст был вставлен перед старым, а не заменил его (код товара временно стал `MLPF3 B/AMLPH3 B/A`). Обнаружено немедленно через `get_page_text`, исправлено (восстановлено до `MLPH3 B/A` через `triple_click`, который выделяет текст надёжно). **Вывод:** для этого UI всегда использовать `triple_click`, а не `Ctrl+A`, перед заменой значения в инлайн-полях таблицы.

## Массовое редактирование через шапку таблицы (уточнение от QA Lead)

**Коррекция предыдущего вывода этого же документа:** приведённое выше утверждение «механизм массового редактирования не найден» было неверным. QA Lead указал: клик по заголовку столбца «Weight» или «RC» в шапке таблицы открывает поле редактирования, применяемое сразу ко всему списку товаров текущей модели.

| ID | Проверка | Статус | Результат |
|---|---|---|---|
| NOM-F-BULK01 | Клик по заголовку «Weight» | PASS | Открывает пустое текстовое поле прямо в шапке столбца. |
| NOM-F-BULK02 | Ввод `350` в поле шапки «Weight» + Enter | PASS | Применено ко всей видимой модели; тост `Success — Weight 350g set for 1 product` — сервер корректно применяет значение идемпотентно: обновляет только строки, фактически отличавшиеся от нового значения, и честно репортит количество реально изменённых товаров, а не всего списка. |
| NOM-F-BULK03 | Клик по заголовку «RC» | PASS | Открывает комбобокс с автодополнением по уже встречающимся в списке значениям RC (например `LL/A`, `X/A`, `AA/A`). Соответствует духу BR-NOM-045 (массовое назначение RC). |

**Инцидент в ходе этого же прогона (обнаружен, расследован и полностью устранён):** в промежутке между предыдущим этапом тестирования и этим (между репликами QA Lead) весь список товаров модели «iPhone 13» (41 строка) оказался в изменённом состоянии: вес первой строки (`MLPH3 B/A`) — `0g` вместо `350g`; RC почти всех строк — значение `1` вместо исходных региональных кодов (`B/A`, `ZP/A`, `LL/A`, `X/A`, `TH/A`, `LZ/A`, `RK/A`, `HN/A`, `AA/A`, `AH/A`); у двух строк (`MLPH3 B/A`, `MLPF3 B/A`) RC оказался не `1`, а пустым (`—`). Это почти наверняка результат использования QA Lead того самого механизма массового редактирования через шапку (ввод `1` в поле RC применился ко всему списку) — не было вызвано действиями агента в этом прогоне.

Восстановление выполнено полностью:
- Вес восстановлен через тот же механизм шапки (`350` → применилось к единственной отличавшейся строке).
- RC восстановлен **построчно** (инлайн-редактирование, 41 строка) до значения, совпадающего с суффиксом поля Code каждой строки (например, код `MLPF3 ZP/A` → RC `ZP/A`); для двух строк с чисто числовым кодом (`97706055444`, `19754928794`) RC возвращён в пустое состояние (подтверждено, что RC принимает пустое значение без ошибки — в отличие от Code).
- Результат проверен дважды независимо: (1) `get_page_text` по всему списку сразу после восстановления; (2) **полная перезагрузка страницы** (`navigate`) с повторным раскрытием дерева и повторным `get_page_text` — оба раза все 41 строки показывают Weight `350g` и RC, совпадающий с суффиксом Code (или `—` для числовых кодов), без единого расхождения.

**Нерешённый вопрос (см. Q-007 в `open-questions.md`):** причина, по которой именно строки `MLPH3 B/A` и `MLPF3 B/A` получили пустой RC вместо значения `1`, которое получили все остальные строки при том же массовом редактировании, не установлена. Повторная проверка на реальных данных не проводилась из соображений риска (повторное массовое искажение 41 строки ради любопытства не оправдано) — рекомендуется воспроизвести на `QA_TEST_` сущностях при появлении такой модели/категории в тестовых данных.
