# Documentation Standard — Fimex Admin QA

Утверждённые форматы документации проекта. Любое изменение этого стандарта требует согласования с QA Lead.

## 1. Назначение документа

Фиксирует:

- обязательную структуру `spec.md` (ожидаемое поведение страницы);
- обязательный формат `checklist.md` (чек-лист проверок страницы);
- правила ID для бизнес-правил и проверок;
- правила приоритетов;
- общие правила оформления.

---

### Правила ID бизнес-правил

Формат: `BR-<DOMAIN>-<NUMBER>`, например `BR-USERS-001`, `BR-ORDERS-001`, `BR-AUTH-001`, `BR-GLOBAL-001`.

Это только формат идентификатора, а не реальные требования Fimex Admin.

- Один ID — одно правило. Не создавать несколько ID для одного и того же правила.
- Ранее выданные ID не перенумеровываются.
- `DOMAIN` — короткое смысловое имя функционального домена (USERS, ORDERS, AUTH, GLOBAL и т.п.); новые домены вводятся по мере изучения админки.

### Контроль размера

Если `spec.md` превышает ориентировочно 300–400 строк — проверить на дублирование и целесообразность выноса общих правил в `requirements/`. Это ориентир, а не жёсткий лимит; полезная документация не сокращается ради соблюдения лимита строк.

## 3. Шаблон checklist.md

Компактный Markdown-чек-лист в `pages/<page-id>/checklist.md`.

Формат одной проверки:

```markdown
- [ ] **<ID> | <P1/P2/P3>** — <конкретное действие или условие> → <однозначный ожидаемый результат>. [<ссылка на BR, если есть>]
```

Иллюстративные примеры формата (демонстрируют только оформление; это не реальные требования Fimex Admin и их запрещено переносить в реальные чек-листы без подтверждения соответствующих бизнес-правил):

- [ ] **USR-F001 | P1** — При успешной загрузке списка отображаются корректные данные пользователей. [BR-USERS-001]
- [ ] **USR-F002 | P1** — После применения фильтра отображаются только соответствующие записи. [BR-USERS-002]
- [ ] **USR-N001 | P1** — При ошибке API отображается предусмотренное состояние ошибки.
- [ ] **USR-UI001 | P3** — При замене скелетона контентом отсутствуют мерцания и скачки разметки.
- [ ] **USR-T001 | P2** — При штатной загрузке отсутствуют необработанные ошибки Console.

### Правила написания

1. Одна проверка — один логически проверяемый результат.
2. Формулировка конкретна; не использовать абстрактное «проверить корректность».
3. Ожидаемый результат однозначен.
4. Не объединять независимые сценарии в одну проверку.
5. Не дублировать проверки.
6. Использовать тестовые данные (`QA_TEST_...`), если они необходимы для проверки.
7. ID проверки стабилен — не переиспользуется и не меняется после создания.
8. Указывать ссылку на требование (`[BR-...]`), если оно существует.
9. Для сложных сценариев допускаются вложенные пояснения или отдельные тест-кейсы.

### Группировка

При необходимости используются разделы: Функциональные проверки / Негативные проверки / Граничные значения / Права доступа / Асинхронность и состояния / Интеграционные проверки / UI/UX / Технические проверки. Пустые разделы не создаются.

### ID проверок

Формат: `<PAGE-PREFIX>-<CATEGORY>-<NNN>`, например `USR-F001` (функциональная), `USR-N001` (негативная), `USR-UI001` (UI/UX), `USR-T001` (техническая). `PAGE-PREFIX` — короткий префикс страницы, фиксируется при создании чек-листа и далее не меняется.

### Приоритеты

- **P1** — критические бизнес-сценарии, целостность данных, безопасность.
- **P2** — значимые функциональные, негативные, интеграционные и технические проверки.
- **P3** — низкорисковые проверки и несущественные визуальные детали.

Приоритет определяется риском конкретной проверки, а не только её категорией.

### Независимая верификация

Для операций, изменяющих данные, добавляются проверки сохранения результата (reload, повторное открытие страницы, другой раздел, разрешённый API-запрос) — только там, где это применимо; механически не добавляются.

### Результаты прогонов

В исходном `checklist.md` все чекбоксы остаются пустыми. Статусы конкретного тестового прогона (`PASS` / `FAIL` / `BLOCKED` / `NOT RUN`) сохраняются отдельно — в `test-runs/<page-id>/<дата или run-id>.md`.

Если чек-лист превышает ориентировочно 100 проверок — проверить на дублирование и целесообразность разделения на самостоятельные функциональные блоки.

---

## 4. Общие правила оформления

- Язык документации — русский.
- Markdown без избыточного форматирования сверх необходимого.
- Один актуальный документ на сущность — копии «на всякий случай» не создаются.
- Ссылки между документами — относительные пути внутри проекта.
- Пароли, токены, session cookie и чувствительные персональные данные пользователей в документацию, скриншоты и логи не попадают.
